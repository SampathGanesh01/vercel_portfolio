One of the most exciting things we built on the ORo robot at Ogmen Robotics was a pipeline that lets users give the robot instructions in plain English. Instead of navigating an app to schedule a task, a user can just say: **"Go find the dog"** or **"Bring a treat to the living room"**.

Here's how we built it, and where it actually gets hard.

## The basic architecture

The pipeline is straightforward at a high level:

1. User input (voice or text) is sent to the LLM with a system prompt that defines the robot's capabilities and the current map state
2. The LLM returns a structured command — a NAV2 goal pose, a behaviour tree trigger, or a sequence of actions
3. The ROS 2 interface executes the command

The key insight is that the LLM doesn't need to understand robotics. It needs to translate ambiguous human intent into unambiguous structured instructions that the robot's existing systems can execute.

## What actually works well

**Intent mapping** is where LLMs genuinely shine. "Living room" is ambiguous — it could be the couch corner or the coffee table or the TV stand. We give the LLM a map of named waypoints and let it pick the most semantically appropriate one based on context. It gets this right surprisingly often.

**Multi-step planning** also works. "Go find the dog and bring it a treat" can be decomposed into: locate dog (vision search), navigate to dog, dispense treat. The LLM handles this decomposition naturally.

**Recovery from failure** was one of the most valuable applications. When the robot gets stuck or loses localization, the LLM can interpret sensor state and the last known goal to suggest a recovery strategy — back up, rotate, try a different path.

## Where it gets hard

**Grounding is the real problem.** The LLM doesn't know where the robot is right now. It doesn't know that the dog is currently in the kitchen, or that the route to the bedroom is blocked by a chair someone moved. You have to carefully design what context you pass in — and that context changes constantly.

**Latency matters.** An LLM call adds 1-3 seconds of latency to what should feel like an immediate response. We learned to separate "intent parsing" (LLM, can be slow) from "execution" (local, must be fast). Never put the LLM in the real-time control loop.

**Hallucinations in safety-critical paths are expensive.** If the LLM decides the robot should navigate to a coordinate that doesn't exist on the map, the robot will error out — or worse, try to path-plan to an impossible goal. We added a validation layer between LLM output and NAV2 that checks every command against the current map state before executing.

## The product lesson

The hardest part wasn't the technical implementation — it was figuring out **what the user actually meant**. The same user saying "go to the other room" means something completely different depending on what room they're in, what time it is, and what the dog was just doing.

Investing time in the system prompt and in the context design — what information you give the LLM about the robot's current state — had a bigger impact on quality than any model upgrade.

---

Natural language robot control is real and it works. It's not magic, but with careful architecture it genuinely makes robots more accessible to people who don't want to learn an app interface.
